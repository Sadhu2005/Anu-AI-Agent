# ANU V0.6.0 — Reliable Autonomous Execution

| | |
|---|---|
| **Status** | Design ready, 15 Oct 2026 |
| **Branch** | `v0.6.0-integration` |
| **Depends on** | V0.5.9 frozen (tag `v0.5.9`) |

## Goal

Once a single autonomous execution works, make it **reliable** before making
ANU smarter.

> **Critical requirement:** if the Raspberry Pi reboots halfway through a
> mutation, ANU must not blindly execute the same mutation again, and must
> never leave a project file changed but unverified.

## 1. Findings: What Happens Today

Investigated on 15 Oct 2026 against tag `v0.5.9`: code review, plus a
read-only inspection of the live Brain.

| Situation | Today's behaviour | Risk |
|---|---|---|
| `systemctl stop` / restart / reboot during a mutation | The unit has no `KillMode`, so systemd sends SIGTERM to **every** process in the service, including the Safe Mutation child. The child has no handler and dies instantly. If it dies between writing the file and the end of the test, the file stays changed and untested. The Task Engine gets empty output and marks the task `blocked` ("Invalid Safe Mutation response"). | **High** |
| Mutation exceeds 300 s | `subprocess.run(timeout=300)` kills the child, with the same effect as above. The task is `blocked` ("timed out"). | High |
| OOM kill or power loss | The unit sets `OOMScoreAdjust=500`, so ANU is a preferred OOM victim. After a power loss the task stays in `running` forever, with no rows written. | High |
| Transaction record | `mutation_transactions` is inserted only at the end (`finalize()`). An interrupted transaction leaves **no row**, only `checkpoints` rows and the manifest. | Medium |
| Running the same change twice | It usually fails safely, because `old` must match exactly once, so it no longer matches after the first apply. That isn't guaranteed (`new` may contain `old`), and the task ends up `blocked` rather than recognised as "already done". | Medium |
| Stale scheduler lock | **Not an issue.** The lock is a kernel `flock`, released automatically when its process dies. The file staying on disk is harmless. | None (needs a test) |
| Stuck `running` task | It is never picked again (the scheduler selects only `pending`), so it is never double-applied, but it is also never recovered. | Medium |
| Retry | There is **no automatic retry**. `failed` is only retried by hand (`retry_task`). Classification: `COMMITTED` → completed, `ROLLED_BACK` → failed, everything else → blocked. | Low |
| Shutdown order | Tests run in `anu-sandbox.service`, but `anu-agent.service` has no `After=anu-sandbox.service`. During a reboot the sandbox can stop first, so a test fails for an environmental reason and is misread as a code defect. | Medium |
| Reboot evidence | The Pi's journal is volatile (`journalctl --list-boots` shows only the current boot). Evidence must come from ANU's own logs under `/srv/anu/logs` and the Brain, which persist. | Process |

Live Brain baseline (15 Oct 2026): no task in `planning` / `ready` /
`running` / `verifying`. Of the 285 transactions with checkpoint rows, 285
have a final `mutation_transactions` row, so there are 0 orphans. There have
been 0 blocked tasks from a killed Safe Mutation. **V0.6.0 starts from a
clean state.**

## 2. Scope

In scope:

1. Graceful stop and shutdown ordering
2. Write-ahead transaction record and idempotency key
3. Startup recovery: reconcile interrupted transactions and orphaned tasks
4. Retry classification with automatic retry for interrupted work only
5. Tests, and live evidence from a restart and a reboot mid-mutation

Out of scope: planning, new capabilities, memory, multiple workers.

## 3. Design

### 3.1 Graceful stop

- Unit: `KillMode=mixed`, so SIGTERM goes only to the runtime and children
  are left alone. Set `TimeoutStopSec=420`, longer than the 300 s mutation
  timeout plus a margin. Add `After=anu-sandbox.service` and
  `Wants=anu-sandbox.service`, so the agent stops **before** the sandbox
  at shutdown.
- Runtime: SIGTERM already sets `running = False`. In addition, no new
  scheduler cycle may start once it is set. Today a cycle can still start
  if SIGTERM arrives during the health check. The cycle in flight runs to
  completion, then the runtime exits.
- If the stop timeout still expires, systemd sends SIGKILL to everything.
  That case is handled by recovery (3.3).

### 3.2 Write-ahead transaction and idempotency

- Safe Mutation inserts its `mutation_transactions` row with status
  `STARTED` **before** the baseline test, and `finalize()` updates that same
  row (by the existing unique `transaction_id`). After a crash, every
  interrupted transaction is visible as a `STARTED` row.
- **Idempotency key:** `sha256(task_id, project, operation, changes)`, where
  `changes` is the canonical JSON of the ordered `{file, old, new}` list. It
  is stored in a new column, `idempotency_key`.
- Before any checkpoint: if a `COMMITTED` row with the same key exists,
  Safe Mutation returns `ALREADY_COMMITTED` without touching files, and the
  Task Engine completes the task with reason `already_committed`.
- A partial unique index enforces at most one `COMMITTED` row per key. Old
  rows have a `NULL` key and are unaffected.

### 3.3 Startup recovery (new `bin/anu-recovery-v0.1.py`)

This runs in `anu-runtime.py` **before the first scheduler tick**: no
cycle is scheduled until recovery has run once. It also runs in the Task
Engine immediately after a Safe Mutation timeout or a missing response, so
a killed child doesn't leave the workspace dirty until the next restart.

**Execution lock** (`runtime/anu-execution.lock`). Tasks are not only run
by the runtime: the Task Engine command line and the regression tests run
them too, without the scheduler lock. So every Task Engine run and every
Safe Mutation run holds this lock **shared** (concurrent runs remain
possible), and recovery takes it **exclusively without waiting**. If
anything is executing, recovery returns `DEFERRED_ACTIVE_EXECUTION` and
reads or changes nothing; the runtime retries on its next cycle. While
recovery holds the lock, any `STARTED` row or non-terminal task is an
orphan by definition. No leases or heartbeats are needed (see section 6).
A killed process releases the lock automatically, because it is a kernel
`flock`.

The lock file is created with mode 0644, so a root-run test and the
`anu-agent` service can share it.

**Transactions** (each `STARTED` row):

| Evidence | Action | Final status |
|---|---|---|
| No checkpoint yet | Nothing was changed | `INTERRUPTED_NOT_APPLIED` |
| Every file's SHA-256 equals its manifest baseline | Nothing applied, or already rolled back | `INTERRUPTED_NOT_APPLIED` |
| Every file equals *baseline with `old` → `new` applied once* | Verify the checkpoint copy against its baseline SHA-256, restore, then verify the file | `INTERRUPTED_ROLLED_BACK` (`integrity_verified=1`) |
| Mixed (some files applied, some baseline) | Restore the applied ones as above | `INTERRUPTED_ROLLED_BACK` |
| Any file matches neither, or a checkpoint is missing or corrupt | **Touch nothing**; alert | `INTERRUPTED_CONFLICT` |

An interrupted change is always **rolled back, never committed**, even if
its test had already passed. A commit requires a witnessed test pass that
was recorded. The retry (3.4) re-applies the change cleanly.

**Tasks** in `planning`, `ready`, `running` or `verifying`:

| Evidence | Task becomes |
|---|---|
| A `COMMITTED` row exists for the task's run | `completed` (the transaction is the source of truth; the process died before the task update) |
| A `ROLLED_BACK` row exists (the test failed; the process died before the task update) | `failed` |
| Its transaction was reconciled to `INTERRUPTED_NOT_APPLIED` or `INTERRUPTED_ROLLED_BACK`, or has no transaction | Interrupted, so retry per 3.4. **Until step 4 lands:** `failed` with reason `interrupted` |
| Its transaction is `INTERRUPTED_CONFLICT`, or ended any other way (`ABORTED_BASELINE_FAILURE`, `MUTATION_ENGINE_ERROR`, `ROLLBACK_VERIFICATION_FAILED`) | `blocked`; operator required |

The task's transaction is the newest `mutation_transactions` row for the
task created at or after its last `TASK_STATE planning` event. An older
attempt's commit never completes a newer attempt.

Every decision is written as a `RECOVERY_TRANSACTION` or `RECOVERY_TASK`
event in `agent_events` and in `logs/anu-recovery.jsonl`, with the
evidence used: SHA-256 values, checkpoint path and previous status. The
runtime also logs one line per decision in `logs/anu.log`.

**Lost mutation in the Task Engine.** On a timeout or a missing response,
the engine records `TASK_MUTATION_LOST` (previously `TASK_BLOCKED`) and
releases its shared lock. It then runs recovery and reports the resulting
task status. If recovery cannot run because another execution holds the
lock, the task is `blocked` as before, and its `STARTED` transaction is
left for startup recovery.

`anu-recovery-v0.1.py` has no command-line mode. Run by hand as root, it
would restore files as root-owned, so only the runtime and the Task Engine
call it, as `anu-agent`.

### 3.4 Retry classification

| Outcome | Class | Task status | Automatic retry |
|---|---|---|---|
| `COMMITTED` / `ALREADY_COMMITTED` | — | `completed` | — |
| `ROLLED_BACK` (test failed after the change) | `code_defect` | `failed` | **No.** The same plan fails the same way; it needs a new plan. |
| `ABORTED_BASELINE_FAILURE` | `environment` | `blocked` | No; operator |
| `MUTATION_ENGINE_ERROR` (no unique `old` match, invalid path or changes file) | `contract` | `blocked` | No |
| `ROLLBACK_VERIFICATION_FAILED`, `INTERRUPTED_CONFLICT` | `integrity` | `blocked` + alert | **Never** |
| Interrupted (signal, crash, power loss, timeout) and reconciled cleanly | `interrupted` | `pending` with `retry_after` | **Yes**, until `MAX_ATTEMPTS = 3` |
| Resource pause (Guardian not `NORMAL`) | not a failure | unchanged | The scheduler simply skips |

- New `tasks` columns: `failure_class` and `retry_after`. The scheduler
  selects `pending` tasks only where `retry_after` is `NULL` or in the past.
- Backoff: 2, then 10 minutes. The attempt counter is never reset, so a
  crash loop ends at `blocked` after 3 attempts with
  `failure_class = 'interrupted'`.
- Auto-retry re-runs the **same** execution spec. That is safe, because
  recovery restored the baseline and the idempotency key blocks a second
  commit.

### 3.5 Schema changes: `migrations/0002_v0_6_0.sql`

```sql
ALTER TABLE mutation_transactions ADD COLUMN idempotency_key TEXT;
CREATE UNIQUE INDEX idx_mutation_transactions_committed_key
    ON mutation_transactions(idempotency_key)
    WHERE status = 'COMMITTED' AND idempotency_key IS NOT NULL;
ALTER TABLE tasks ADD COLUMN failure_class TEXT;
ALTER TABLE tasks ADD COLUMN retry_after TEXT;
```

These changes are additive only. The code applies them with the existing
`ensure_column` pattern if missing, and the file records them. The Brain is
backed up before deployment.

## 5. Tests

All new tests use temporary databases and directories, never the live Brain
([LESSONS-LEARNED.md](../LESSONS-LEARNED.md) D). Crash tests need no test
hooks in production code. They use a project whose test sleeps, and kill
the real Safe Mutation process while that test runs.

- `test_graceful_stop_v0_6_0.py`: SIGTERM during a cycle; the cycle
  completes and no new cycle starts
- `test_mutation_write_ahead_v0_6_0.py`: a `STARTED` row exists before
  the checkpoint, and the same row is finalized
- `test_mutation_idempotency_v0_6_0.py`: a second run with the same key
  gives `ALREADY_COMMITTED` and leaves the file byte-identical
- `test_recovery_reconciler_v0_6_0.py`: every row of the transaction
  table in 3.3, including a corrupt checkpoint
- `test_orphan_task_recovery_v0_6_0.py`: every row of the task table in 3.3
- `test_crash_mid_mutation_recovery_v0_6_0.py`: SIGKILL between
  `MUTATION_APPLIED` and the end; after recovery the file equals the
  baseline, and the retry commits exactly once
- `test_retry_classification_v0_6_0.py`: every row of 3.4, including
  backoff and the 3-attempt stop
- `test_scheduler_lock_recovery_v0_6_0.py`: kill the lock holder; the
  next cycle acquires the lock

## 6. Decisions to Record

- **ADR-012, recovery by reconciliation under an exclusive execution lock,
  not leases.** Every execution holds `runtime/anu-execution.lock` shared,
  and recovery runs only while holding it exclusively. That makes every
  in-flight record it finds an orphan. Leases and heartbeats are deferred
  until there is more than one worker.
- **ADR-013, interrupted mutations are rolled back, never committed.**
  Only a recorded, witnessed test pass may produce `COMMITTED`.

## Exit Criteria

- [ ] `systemctl restart` during a mutation test: the file is restored or
      never changed, the task retries automatically, and exactly **one**
      `COMMITTED` row exists for its idempotency key
- [ ] The same, with `systemctl kill -s KILL` (no graceful stop)
- [ ] The same, with a real Pi reboot, with evidence from ANU logs and the Brain
- [ ] Graceful stop: a stop during a cycle lets the cycle finish
- [ ] Interrupted transactions are reconciled to a terminal status on start;
      none stay `STARTED`
- [ ] Retries happen only for the `interrupted` class and stop at 3 attempts
- [ ] All new tests pass, and the full regression passes on the Pi
